## 一、结论先看

玩家说法「必须一阶有的属性，五阶才能合出来」——**不成立**，但抓到了半个真相。

| 说法 | 判定 | 依据 |
|---|---|---|
| 五阶属性必须来自一阶 | ❌ 错 | 每次升阶**额外获得 2 条随机属性**，不受低阶限制 |
| 想要的属性必须在低阶就带上 | ✅ 对（可控性层面） | 保留的 N 条只能从「两个消耗本元的属性并集」里选 |
| 五阶独有词条（冲灵/化灵/减免百分比/无视）一阶也能有 | ❌ 错 | 这些只能靠 4→5 阶那 2 条随机出 |

一句话：**「想要稳，必须低阶带；想要出，随机也能出。」**

## 二、官方规则原文（决定性证据）

**出处**：`element\interfaces.pck` → 解包条目 `1712` = `Win_FourSoulCore_Update_Help`，`1714` = `Win_FourSoul_Core_Help`（两份内容一致，1714 是简版）

原文（升阶段）：

```
升阶
可以消耗一定数量的瑞灵珠和指定道具，将2个相同的低阶的四灵本元升阶为1个
高阶的四灵本元（最高5阶）；每次升阶会从消耗的四灵本元中的所有属性中保留
与阶数相等条数的属性，并将保留的属性数值翻倍，然后额外获得2条随机属性，
升阶获得的四灵本元均为“已鉴定”。
```

配套约束（同 pck 字符串表 `19790` / `2234`）：

| 字符串 id | 文案 | 含义 |
|---|---|---|
| 50990 | 请放入相同的四灵本元 | 两个消耗品必须同灵、同阶、同名 |
| 50991 | 请鉴定后再进行合成 | 未鉴定不可升阶（客户端把升阶也叫“合成”） |
| 50993 | 此物品未鉴定 | — |
| 41198 | 无四灵本元 | 伏龙鼎对应鼎面空置 |
| 41252 | 是否消耗800瑞灵珠充灵7天 | 瑞灵呈祥（五阶额外增益）充能 |

界面控件（`1711` = `Win_FourSoulCore_Update`）只有：消耗1/2/3（两个本元 + 瑞灵珠）、获得、花费金钱、升级/取消。
**没有「选择保留哪几条」的列表或勾选框** → 保留由服务端按规则抽取，玩家不可自选。

## 三、规则数学（与实测 tooltip 完全吻合）

设升阶前为 N 阶：保留 **N 条**，新增 **2 条随机** → 结果 **N+2 条**。

| 升阶 | 保留条数 | 新增 | 结果条数 | 实测 tooltip |
|---|---|---|---|---|
| 1 → 2 | 1 | 2 | 3 | 3（旧记录里“疑似 4 条”为面板透字误读） |
| 2 → 3 | 2 | 2 | 4 | 4 ✅ |
| 3 → 4 | 3 | 2 | 5 | 5 ✅ |
| 4 → 5 | 4 | 2 | 6 | 6 ✅ |

由此反推：**「阶数」指消耗品阶数，不是结果阶数**（若按结果阶算，二阶会是 4 条、三阶 5 条，与实测冲突）。
这同时闭合了旧文档 `openQuestions` 第 2 条「二阶实测 4 条与阶+1=3 冲突」。

属性条数 = 阶 + 1，此前的经验规律得到机制解释，不再是拟合。

## 五、玩家说法为什么会产生

1. **保留只能从消耗品里选**：想要某条属性进五阶，这条属性必须出现在两个四阶本元的并集里 → 一路追溯，最早就是一阶。玩家把「可控路径」说成了「唯一路径」。
2. **随机 2 条不可控**：随机出的属性无法指定，玩家体感上等于「没有」，于是只统计到「带上来的」那部分。
3. **并集噪声**：两只同阶本元属性不一致时，并集大于保留条数，目标属性有概率被挤掉。属性越杂，越像「一阶没带就出不来」。

实操推论（非官方文案，按规则推）：

- 两只材料本元**属性尽量一致**，把并集压到最小，目标属性保留概率最高。
- 目标属性越早（低阶）带上，可复制的次数越多，五阶成品的成本越低。
- 五阶独有词条只能赌 4→5 阶的 2 条随机，与一阶无关。

## 六、未闭合项

- **每阶随机池与概率**：客户端无此表（`elements.data` / `configs.pck` 均无逐阶权重），仍以论坛统计表为准。客户端只能证明「有 2 条随机」，证不了「随机池里各属性权重」。
- **保留抽取是否真随机**：客户端无选择 UI，只能确认「玩家不可选」；服务端是随机抽还是按某优先级（如数值高低）抽，客户端不可见。

## 七、复现方法（下次可直接照抄）

`pck` 结构：12 字节头 + 连续 zlib 流，无独立索引表。

```python
import zlib
d = open(r'D:\PGP\games\诛仙\element\interfaces.pck','rb').read()
pos, idx = 12, 0
while pos < len(d)-4:
    o = zlib.decompressobj(); buf=[]; p=pos; ok=False
    while p < len(d):
        chunk = d[p:p+262144]
        try: buf.append(o.decompress(chunk))
        except Exception: break
        p += len(chunk)
        if o.eof:
            ok=True; p -= len(o.unused_data); break
    if not ok: pos += 2; continue
    open(f'out/{idx:04d}.bin','wb').write(b''.join(buf)); idx += 1; pos = p
```

- 解出 24755 条 UI 定义；四灵相关：`1711/1712/1713/1714/1715/1716/1717/1719/1721/2310`。
- `elements.data` 本元段：文件偏移 `0x7774624` 起，160 字节/条 × 20 条；名称在 +0（64 字节 wchar），字段区在 +64。
- 属性来源段：偏移 `0xAE1B8` 附近，88 字节/条 × 34 条，名称在 +24。
