# 诛仙3团队副本模拟训练场方案 v1.1

## 一、方案背景与核心愿景

在《诛仙3》玩家群体中，单次技能的伤害估算（Snapshot）已无法完全满足高端玩家对副本通关效率的追求。团队本战斗本质上是一场**在时间轴约束下，多人配合、状态交织的“伤害竞速”**。

本方案旨在现有战力与单技能伤害计算器的基础上，升级构建一套**团队副本模拟训练场（Team Dungeon Simulation Playground）**。通过**事件驱动的时间轴模拟引擎**，完全复现真实的副本战斗环境：
- **主输出职业**：精确模拟施法时间、段数、CD、充能层数、全局冷却（GCD）及出招策略。
- **辅助职业**：作为团队增益（Buff）与怪物减益（Debuff）的时间轴提供者，重现复杂的上状态时机与覆盖率。
- **Boss 机制**：模拟血量扣减、免伤防线（暴击伤害减免）、伤害压缩与多阶段状态。

### 核心结论
- **TS Web 训练场 + 共享 TS 模拟引擎**：这是最佳的技术选型。玩家需要直观的可视化界面来拖拽排轴、调整队伍和实时看秒伤曲线，而 Python 脚本则作为 CLI 外壳，配合现有 Agent Skill 进行批量自动化分析。
- **扩展与兼容**：不推翻现有架构，将计算公式和逻辑提取到独立模块中，保护已验证的计算基础，实现双向复用。

## 二、架构设计：NPM Workspaces (Monorepo)

为解决公式散落在 `agent_tool` 与 `web_app` 导致的代码漂移风险，并支持跨平台复用，我们采用 **Monorepo** 架构。

```
new_zx_calc_noactcode_agent/
├── packages/
│   └── simulation-engine/          # 纯 TypeScript 共享模拟引擎（核心）
│       ├── src/
│       │   ├── calculator.ts       # 从现有两处合并的伤害公式 (Hit Resolver)
│       │   ├── timeline.ts         # 事件驱动时间轴核心
│       │   ├── actors.ts           # Actor 与策略处理器
│       │   ├── effects.ts          # Buff/Debuff 状态机
│       │   ├── boss.ts             # Boss 状态与阶段控制器
│       │   ├── types.ts            # 共享类型定义
│       │   └── index.ts            # 统一导出入口
│       ├── package.json
│       └── tsconfig.json
├── agent_tool/                     # CLI工具，引入 @zx/simulation-engine
│   ├── src/
│   │   ├── sim_cli.ts              # CLI 模拟入口，供 Agent Skill 调用
│   │   └── ...
│   └── package.json
├── web_app/                        # React 前端，引入 @zx/simulation-engine
│   ├── src/
│   │   ├── features/simulator/     # 训练场 UI 组件
│   │   └── ...
│   └── package.json
└── package.json                    # Workspace 根配置
```

> [!TIP]
> 这种设计保证了 `agent_tool` 命令行接口与 `web_app` 浏览器前端共用同一套伤害公式与时间轴逻辑。任何伤害公式的微调只需在一个地方修改，便能立即在两端生效。

## 三、数据层扩展：统一技能与 Buff 系统 (Q3)

针对辅助职业数据整合问题，**不建议新建文件，而建议将辅助职业技能统一合并并扩展在现有的 `skills.json` 中**。`skills.json` 将作为团队副本模拟的唯一战斗技能数据源：伤害技能、Buff 技能、Debuff 技能、重置类技能都按职业归档在同一个技能库中。现有 `combat_buffs.json` 仅作为旧版静态计算器的默认 Buff 兼容层，不再作为团队模拟器的状态数值来源，避免同一个状态在两处重复维护。

### 3.1 技能与 Buff 扩展字段设计

我们在 `skills.json` 中对技能节点进行字段补充，用以表达 Buff 生效规则、充能层数和多阶段触发特性：

```typescript
export type SkillActionType = 'DAMAGE' | 'BUFF' | 'DEBUFF' | 'UTILITY';

export interface MultiPhaseConfig {
  Phases: {
    PhaseIndex: number;            // 阶段序号（从 1 开始）
    Duration: number;              // 本阶段持续时间（秒）
    AutoTransition: boolean;       // 时间到后是否自动进入下一阶段
    AppliesEffects: AppliedEffectConfig[]; // 本阶段挂载的状态，复用统一 Buff/Debuff 规则
  }[];
  ManualActivationAllowed: boolean; // 是否允许玩家点击提前激活下一阶段
}

export interface CooldownResetEffect {
  TargetSkillId: string;           // 目标技能 ID
  ResetType: 'REFRESH_CHARGES' | 'REDUCE_COOLDOWN'; // 刷新充能或减少 CD
  Charges?: number;                // 刷新层数
  ReductionSeconds?: number;       // 减少的 CD 秒数
}

export interface AppliedEffectConfig {
  EffectId: string;
  EffectName: string;
  Target: 'SELF' | 'ALLY' | 'TEAM' | 'ENEMY'; // 自身、指定队友、全队、Boss
  Duration: number;              // 持续时间（秒）
  Stackable?: boolean;           // 是否允许叠加
  MaxStacks?: number;            // 最大叠加层数
  RefreshOnReapply?: boolean;    // 重复施放时是否刷新持续时间
  ExclusiveGroup?: string;       // 互斥组，例如阵法、同类易伤；只有同组才互斥，不按属性字段自动互斥
  ExclusivePolicy?: 'MANUAL_PRIORITY' | 'HIGHEST_EFFECT_VALUE' | 'NO_OVERWRITE';
  Priority?: number;             // MANUAL_PRIORITY 模式下的手工覆盖优先级
  EffectPower?: number;          // HIGHEST_EFFECT_VALUE 模式下用于比较强弱的效果强度
  BuffEffects: BuffEffects;      // 具体属性数值，Debuff 也复用此结构描述对 Boss 的影响
}

export interface HitTimingConfig {
  Mode: 'EVENLY_DURING_CAST' | 'ON_CAST_COMPLETE' | 'CUSTOM';
  Offsets?: number[];            // CUSTOM 模式下每段命中相对 CAST_START 的秒数
}

export interface SkillExtension {
  // --- 基础模拟信息 ---
  ActionType: SkillActionType;      // 技能类型：伤害、Buff、Debuff、功能技能
  Cooldown: number;                 // 冷却时间（秒）
  CastTime: number;                 // 施法动作时间（秒）
  IsAOE: boolean;
  HitTiming?: HitTimingConfig;      // 多段技能命中时间，默认按 CastTime / HitCount 均匀出段
  
  // --- 充能机制 (例如：逐霜苍龙啸) ---
  MaxCharges?: number;              // 最大充能层数，若无则默认为 1
  ChargeReplenishTime?: number;     // 充能恢复一格所需时间（秒）
  
  // --- 技能连锁与重置 (例如：鹰扬折冲) ---
  CooldownResets?: CooldownResetEffect[];
  
  // --- 状态与光环提供者 (Buff/Debuff) ---
  AppliesEffects?: AppliedEffectConfig[];
  
  // --- 多阶段技能激活 (例如：昭冥日月弘光) ---
  MultiPhaseConfig?: MultiPhaseConfig;
}
```

### 3.3 玩家 Profile 绑定与技能数据运行时覆盖 (Q1)

为了处理不同玩家因点天书、带护符或穿特定星辰/装备，导致同一技能的冷却时间（Cooldown）、施法时间（CastTime）、状态持续时间或增益/减益数值各不相同的问题，引擎在初始化时通过“白板配置 + 动态覆写”实现动态绑定：

1. **全局数据库**：`skills.json` 保持干净、静态，仅存储白板技能的默认属性。
2. **运行时混入**：当 Actor 实例在模拟器中被初始化时，引擎深拷贝全局白板配置，并读取该玩家 Profile 中的个性化技能覆盖表进行深层合并。覆盖只作用于本次模拟的运行时技能对象，不回写 `skills.json`。
3. **覆盖范围**：Profile 可以覆盖少量必要字段，例如 CD、施法时间、充能、段数命中时间、技能附加属性、Buff/Debuff 持续时间与具体效果数值；不要求为每个玩家复制完整技能。

#### 运行时覆盖实现示例

```typescript
export interface PlayerSkillOverride {
  Cooldown?: number;                 // 玩家特定缩减后的 CD (秒)
  CastTime?: number;                 // 玩家特定缩减后的施法动作时间 (秒)
  MaxCharges?: number;
  ChargeReplenishTime?: number;
  HitTiming?: HitTimingConfig;
  SkillBonusAttributes?: Partial<SkillBonusAttributes>;
  AppliesEffects?: Record<string, Partial<AppliedEffectConfig>>; // 按 EffectId 覆盖持续时间或效果数值
  MultiPhaseConfig?: Partial<MultiPhaseConfig>;
}

function mergeEffectOverrides(skill: Skill, overrides: Record<string, Partial<AppliedEffectConfig>>) {
  if (!skill.AppliesEffects) return;
  skill.AppliesEffects = skill.AppliesEffects.map(effect => ({
    ...effect,
    ...(overrides[effect.EffectId] || {}),
    BuffEffects: {
      ...effect.BuffEffects,
      ...(overrides[effect.EffectId]?.BuffEffects || {})
    }
  }));
}

export class Actor {
  public Skills: Record<string, Skill> = {};

  constructor(baseSkills: Skill[], customizations: Record<string, PlayerSkillOverride>) {
    baseSkills.forEach(skill => {
      // 1. 深拷贝白板技能数据，避免污染全局 JSON 缓存
      const runSkill = JSON.parse(JSON.stringify(skill));
      
      // 2. 检索并融合该玩家 Profile 下的个性化覆盖数据
      const override = customizations[skill.SkillID];
      if (override) {
        const { AppliesEffects, SkillBonusAttributes, ...topLevelOverride } = override;
        Object.assign(runSkill, topLevelOverride);
        if (SkillBonusAttributes) {
          runSkill.SkillBonusAttributes = {
            ...runSkill.SkillBonusAttributes,
            ...SkillBonusAttributes
          };
        }
        if (AppliesEffects) mergeEffectOverrides(runSkill, AppliesEffects);
      }
      
      this.Skills[skill.SkillID] = runSkill;
    });
  }
}
```

#### 3.3.1 四代技能品质（萤炬/皓月/曦日）动态预设融合机制

随着 4 代技能的加入，玩家拥有的技能会受到四代神通/经典品质的动态缩减与倍率影响（如天音的“摩柯心经”：基础 CD 为 180s，但装配不同品质四代技能后，CD 会分别扣减 30s/60s/90s，且攻击力百分比加血倍率变为 4倍/6倍/8倍）。

为解决 JSON 无法动态书写公式、且不希望在引擎中“硬编码”品质数值逻辑的问题，引擎在 `skills.json` 级别引入了 **“四代预设 (FourthGenPresets)”**，并在运行时（Actor 构造阶段）根据玩家 Profile 中的 **“品质标记 (FourthGenQuality)”** 进行自动化两阶段融合：

##### 3. 运行时 Actor 两阶段自动化融合
```typescript
baseSkills.forEach(skill => {
  const runSkill = JSON.parse(JSON.stringify(skill)) as Skill;
  const override = customizations[skill.SkillID];
  
  // A. 第一阶段：如果检测到玩家配置了四代品质，自动提取对应预设并融合
  if (override?.FourthGenQuality && runSkill.FourthGenPresets?.[override.FourthGenQuality]) {
    const preset = runSkill.FourthGenPresets[override.FourthGenQuality];
    applySingleOverride(runSkill, preset);
  }

  // B. 第二阶段：融合玩家的其他特异性自定义覆盖（优先级最高，覆盖预设）
  if (override) {
    applySingleOverride(runSkill, override);
  }
  
  this.Skills[skill.SkillID] = runSkill;
});
```
这种设计极大地简化了玩家在 Profile 中的配置成本，又完美保留了数据库单源配置与高自由度覆盖的全部优势。


### 3.4 不同职业同类 Buff/Debuff 运行时互斥与覆盖过滤机制 (Q3)

在多职业副本配合中，不同职业可能施加相似状态，但这些状态是否互斥不能简单按属性字段判断。例如 A 职业和 B 职业都提供气血增益，并不代表二者一定互相覆盖；只有权威数据明确标记为同一个 `ExclusiveGroup` 的状态，才进入互斥覆盖判断。

#### 核心运行逻辑
1. 每一个应用的状态（`AppliedEffectConfig`）都可以打上一个 `ExclusiveGroup`（例如 `"MONSTER_HARMED_GROUP"`）。
2. 没有 `ExclusiveGroup` 的状态默认可以共存；即使两个状态都修改 `BuffHealthPercentEffect`，只要没有被配置到同一互斥组，就同时生效。
3. 同一目标身上已存在同组状态时，按 `ExclusivePolicy` 决定如何处理：
   - `HIGHEST_EFFECT_VALUE`：比较 `EffectPower`，强效果顶替弱效果，弱效果不生效。
   - `MANUAL_PRIORITY`：比较 `Priority`，用于无法用单一数值判断强弱的状态。
   - `NO_OVERWRITE`：已有状态持续期间不允许新状态顶替，直到旧状态自然过期。
4. 所有主动施放的状态都生成唯一 `InstanceId`。旧状态被顶替后，其历史 `BUFF_EXPIRE` 事件仍可能留在事件队列中；过期事件必须校验 `InstanceId`，避免误删后续新状态。

#### 运行时互斥过滤实现示例

```typescript
export interface ActiveEffect {
  InstanceId: string;
  EffectId: string;
  SourceActorId: string;
  SourceSkillId: string;
  ExclusiveGroup?: string;
  ExclusivePolicy?: AppliedEffectConfig['ExclusivePolicy'];
  Priority?: number;
  EffectPower?: number;
  AppliedAt: number;
  EndTime: number;               // 触发 BUFF_EXPIRE 事件的绝对时间
  BuffEffects: BuffEffects;      // 对伤害起效的实际数值
}

export class EffectManager {
  private activeEffects: ActiveEffect[] = [];

  public applyEffect(
    newEffect: AppliedEffectConfig,
    currentTime: number,
    sourceActorId: string,
    sourceSkillId: string
  ): ActiveEffect | null {
    if (!newEffect.ExclusiveGroup) {
      return this.addRawEffect(newEffect, currentTime, sourceActorId, sourceSkillId);
    }

    const existingIndex = this.activeEffects.findIndex(
      e => e.ExclusiveGroup === newEffect.ExclusiveGroup
    );

    if (existingIndex === -1) {
      return this.addRawEffect(newEffect, currentTime, sourceActorId, sourceSkillId);
    }

    const existing = this.activeEffects[existingIndex];
    if (!this.shouldReplace(existing, newEffect)) return null;

    this.activeEffects.splice(existingIndex, 1);
    return this.addRawEffect(newEffect, currentTime, sourceActorId, sourceSkillId);
  }

  public expireEffect(instanceId: string) {
    this.activeEffects = this.activeEffects.filter(effect => effect.InstanceId !== instanceId);
  }

  private shouldReplace(existing: ActiveEffect, incoming: AppliedEffectConfig): boolean {
    const policy = incoming.ExclusivePolicy || existing.ExclusivePolicy || 'MANUAL_PRIORITY';
    if (policy === 'NO_OVERWRITE') return false;
    if (policy === 'HIGHEST_EFFECT_VALUE') {
      return (incoming.EffectPower || 0) > (existing.EffectPower || 0);
    }
    return (incoming.Priority || 0) >= (existing.Priority || 0);
  }

  private addRawEffect(
    newEffect: AppliedEffectConfig,
    currentTime: number,
    sourceActorId: string,
    sourceSkillId: string
  ): ActiveEffect {
    const activeEffect = {
      InstanceId: crypto.randomUUID(),
      EffectId: newEffect.EffectId,
      SourceActorId: sourceActorId,
      SourceSkillId: sourceSkillId,
      ExclusiveGroup: newEffect.ExclusiveGroup,
      ExclusivePolicy: newEffect.ExclusivePolicy,
      Priority: newEffect.Priority,
      EffectPower: newEffect.EffectPower,
      AppliedAt: currentTime,
      EndTime: currentTime + newEffect.Duration * 1000,
      BuffEffects: newEffect.BuffEffects
    };
    this.activeEffects.push(activeEffect);
    return activeEffect;
  }
}
```

## 四、模拟引擎核心运作机制

模拟器通过**离散事件仿真（Discrete Event Simulation）**运行。引擎维护一个优先队列（Priority Queue），按照时间从小到大弹出事件并处理，直到达到最大时长限制或 Boss 被击杀。

### 4.1 事件类型与结构

```typescript
export type SimEventType =
  | 'CAST_START'          // 技能开始施法
  | 'CAST_COMPLETE'       // 施法动作结束，解除施法锁定并触发下一次决策
  | 'HIT'                 // 多段技能中的单次判定（用于多段跳字）
  | 'BUFF_APPLY'          // 增益/减益效果施加
  | 'BUFF_EXPIRE'         // 效果过期
  | 'COOLDOWN_READY'      // 冷却时间恢复/充能恢复
  | 'PHASE_TRANSITION'    // 技能或 Boss 阶段切换
  | 'BOSS_DEAD'           // 战斗结束
  | 'ACTOR_DECISION';     // 触发主输出决策下一个动作

export interface SimEvent {
  time: number;           // 毫秒时间戳
  type: SimEventType;
  actorId: string;
  skillId?: string;
  data?: any;
}
```

### 4.2 战斗规则设计

1. **施法锁定 (Cast Lock) 与全局冷却 (GCD)**：
   - 角色一旦启动 `CAST_START`，将处于“施法锁定”状态，时长为技能的 `CastTime`。在锁定期间，无法插入其他主动施法动作。
   - 技能成功进入 `CAST_START` 时立即开始计算 `Cooldown`，并立即消耗充能层数；`CAST_COMPLETE` 不再作为 CD 起点。
   - 设定全局冷却时间（GCD，通常为 0.3s - 0.5s），限制瞬发技能（`CastTime` 为 0）的极限连击速度，防止出招死循环。

2. **多段命中时间 (Hit Timing)**：
   - 默认模式为 `EVENLY_DURING_CAST`。例如 3 秒 9 段技能，段间隔为 `3 / 9 = 0.333s`，每段伤害按当时战场上的 Buff/Debuff 状态独立结算。
   - 若某个技能的命中节奏与平均分布不一致，则在 `HitTiming.Mode = CUSTOM` 时通过 `Offsets` 明确每段相对 `CAST_START` 的命中秒数。
   - `ON_CAST_COMPLETE` 只用于确实需要施法完成后一次性结算的技能，不能作为多段技能的默认行为。

3. **逐段伤害流水 (Hit Damage Ledger)**：
   - 模拟器不再把“技能总伤”作为基础结算单位，而是为每一个 `HIT` 事件生成一条伤害记录。
   - 总伤、某时间段伤害、技能占比、每秒滚动伤害、Buff 窗口收益都从伤害流水表聚合得到。
   - 现有静态公式需要拆成 `resolveHitDamage` 级别的结算能力，保证多段技能在中途 Buff/Debuff 变化时能按每段实际命中时刻独立计算。

```typescript
export interface HitDamageRecord {
  Time: number;                  // 命中发生的毫秒时间戳
  ActorId: string;
  SkillId: string;
  SkillName: string;
  HitIndex: number;
  HitCount: number;
  MinDamage: number;
  MaxDamage: number;
  AvgDamage: number;
  ActiveEffectIds: string[];     // 本段命中时参与结算的 Buff/Debuff 实例
  BossHpBefore: number;
  BossHpAfter: number;
}
```

4. **极速 (Haste) 结算**：
   - 如果角色身上存在带有极速加成的 Buff，施法时间将动态压缩：
     $$\text{实际施法时间} = \frac{\text{基础施法时间}}{1 + \frac{\text{极速百分比}}{100}}$$
   - 锁定的施法时间在 `CAST_START` 判定瞬间结算，施法期间极速 Buff 消失不影响已开始施法的动作。

5. **Buff 刷新与同类排他性**：
   - **时间重置**：大部分常规状态在重复施放时刷新持续时间（`RefreshOnReapply: true`）。
   - **排他与覆盖**：定义互斥组（如不同阵法）。低优先级 Buff 无法覆盖高优先级 Buff。

## 五、特殊技能机制的模拟方案

### 5.1 充能与重置机制（以“逐霜·苍龙啸”与“鹰扬折冲”为例）

- **充能状态维护**：
  为每个充能技能在 Actor 的运行时状态中维护一个 `charges` 变量和独立的时间恢复队列。
- **触发机制**：
  1. 玩家释放“苍龙啸”：检查 `charges > 0`。若满足，则消耗 1 层充能，启动 3s 的施法锁定。若充能从满层跌落，则在背景启动充能恢复计时器（18s 后触发恢复事件）。
  2. 玩家释放“鹰扬折冲”：触发 `CooldownResets` 效果。引擎直接定位到“苍龙啸”的状态数据，将 `charges` 设为 3，并清除背景的充能恢复计时器。

```
[苍龙啸 满充能=3] ────释放────> [充能=2] (背景启动 18s 充能恢复事件)
   │
   ├────连续释放────> [充能=1]
   │
[鹰扬折冲 释放] ───────────────> [充能直接刷新=3] (清除背景 18s 恢复事件)
```

### 5.2 多阶段技能机制（以“昭冥·日月弘光”为例）

多阶段技能作为“特殊 Actor 状态”进行托管。

- **自动流转**：
  1. 施放“日月弘光”：在 Actor 或团队目标身上按 `Phase 1.AppliesEffects` 挂载状态，持续 30s。同时，向事件队列推入一个 30s 后的 `PHASE_TRANSITION` 事件。
  2. 30s 后流转事件到达：按统一状态实例规则移除或替换一段状态，再挂载 `Phase 2.AppliesEffects`，例如 30% 攻击与 150% 爆伤，持续 15s。
- **手动提前流转（过载/爆发激活）**：
  1. 若玩家策略中配置了“提前手动激活”，在 `Phase 1` 存续期间，触发“日月弘光·二段”技能动作。
  2. 引擎拦截当前事件，将原定 30s 后的 `PHASE_TRANSITION` 事件直接提前到当前时刻执行，提前兑现 `Phase 2` 的高额加成，进入 15s 的黄金爆发期。

## 六、队伍模拟与策略引擎

首版采用 **单 DPS 狂飙，多辅助增益** 的单核心策略：

```
                    ┌──────────── 预加 Buff (天音等) ────────────┐
                    ▼                                            ▼
┌──────────────────────┐      伤害结算      ┌──────────────────────┐
│  主输出 (DPS Actor)  │ ────────────────> │    Boss (Monster)    │
└──────────────────────┘                   └──────────────────────┘
                    ▲                                            ▲
                    └──────────── 覆盖 Debuff (焚香等) ──────────┘
```

### 6.1 辅助职业出招策略 (Support Policies)

辅助不计算自身输出，只向战场投掷状态。其策略支持三种配置：
1. **起手铺垫期（Setup Phase）**：整场模拟从 `t = 0s` 统一开始，不引入负时间轴。辅助职业在 0s 起按顺序或绝对时间施放 Buff/Debuff，主输出也可以在此期间释放自身增益、法宝增益等非输出准备技能。任何技能一旦施放，其持续时间和 CD 都从实际施放/生效时刻开始计算。Boss 击杀时间统计始终从 `t = 0s` 开始；主输出个人秒伤统计则从主输出第一个输出技能命中或开始造成伤害的时刻开始。
2. **CD 好了就放（Auto-CD）**：辅助在其技能冷却结束时，自动施放 Buff/Debuff。
3. **绝对时间释放（Timestamped Action）**：在玩家预设的绝对时间点（如第 10 秒开启某种大招增益，配合主输出爆发）。

### 6.2 主输出策略 (DPS Rotation Policies)

玩家可以通过以下方式操纵主输出的决策：

1. **手动时间轴（Manual Timeline）**：
   - v1 即支持手动排轴，但首版交互可以先采用表格或 JSON 指令列表；拖拽式时间轴编辑器作为同一能力的 UI 增强，不作为引擎前置条件。
   - 每条指令包含绝对时间、技能 ID、目标与可选条件。若到点时技能不可用，引擎记录“手动指令失败/延迟”并按配置选择跳过或等待。
2. **固定技能循环（Fixed Rotation Loop）**：
   - 模拟玩家预先设置的一套固定技能循环。
   - 循环维护当前位置指针；每次决策从当前位置开始向后扫描，技能 CD 中或充能不足则跳过，释放成功后指针移动到该技能的下一个位置。
   - 若整轮都没有可用技能，则进入等待、平 A 或填充技能策略。
3. **法宝自动挂机模式（Skill Bar Loop）**：
   - 模拟《诛仙3》天人合一或法宝栏的排轴规则。
   - 默认按 1 到 8 号栏位从头扫描，若技能可用（有充能层数且 CD 完毕），则立刻施放；CD 中的技能直接跳过。
   - 为避免后续实测规则差异，策略层保留 `ScanMode`：`FROM_FIRST_EACH_DECISION` 与 `CONTINUE_POINTER`。首版 UI 默认使用前者。

## 八、Web UI 训练场：核心交互与可视化设计

训练场前端延续现有计算器的视觉基础，重点提升信息密度、时间轴可读性和方案对比效率。首版不引入额外图表库，避免前端依赖膨胀。

### 8.1 核心配置区

- **队伍构成面板**：
  - 支持玩家将辅助职业拖入 6 人或 12 人小队。
  - 点击辅助职业，可快速勾选开启该职业提供的哪些特定 Buff（例如：天音法力增幅，天华反弹光环）。
- **技能循环编排器 (Timeline Editor)**：
  - 使用模式切换控件支持手动时间轴、固定技能循环、法宝栏/天人合一三种策略。
  - 手动时间轴 v1 可先采用表格/JSON 指令编辑；拖拽式时间轴作为后续 UI 增强。
  - 法宝栏模式支持拖动排列 1-8 号栏位的顺序，实时更新循环模拟结果。
- **角色面板导入**：
  - 允许直接拉取或载入已有的玩家属性 JSON 文件（如你的 Shuanghua Profile 模板）。

### 8.2 可视化结果大屏（杀手级功能）

1. **DPS 实战演进曲线**：
   - 使用项目现有 Recharts 渲染击杀 DPS 曲线、Boss 血量曲线和分段伤害统计。
   - Boss 击杀耗时从 `t = 0s` 统计；主输出个人 DPS 从其第一段输出伤害开始统计。
   - 提供 1 秒滚动伤害视图，展示“这一秒打了多少亿伤害”，并可按技能、Buff 窗口或时间段聚合。
   - 标注出战斗中触发的“爆发峰值点”与因等待 CD 造成的“干枯空窗区”。
2. **动态时序排轴回放（Battle Timeline）**：
   - 横轴为时间（秒），以甘特图形式完美复现整场战斗：
      - **主输出行**：展示技能卡片占用的时长、CD 冷却阴影。
      - **状态效果行**：展示各类增益与怪物减益条的消长，鼠标悬浮可查看详细效果。
   - 首版用 SVG 或 DOM/CSS 实现时间轴，不额外引入 Canvas 专用渲染框架。

```
时间轴 (0s) ─────── 5s ─────── 10s ─────── 15s ─────── 20s ─────── 25s ───────>
主输出:  [ 苍龙啸 3s ][ 临渊 1s ][等CD][ 苍龙啸 3s ][ 山雨 2s ]
天音:   [███████████ 增幅 Buff 20s ███████████]       [ 等待 CD ]
焚香:           [████████ 弱化 Debuff 15s ████████]   [ 再施放... ]
BossHP: 100% ───────── 85% ────────── 68% ────────── 50% ──────── 28% ───> 0% (击杀!)
```

3. **方案对比实验室（A/B Testing Lab）**：
   - 允许玩家锁定当前方案 A 作为基准，修改技能顺序或替换辅助队员生成方案 B。
   - 直观对比：**击杀时间缩短百分比、DPS 平均提升幅度、Buff 平均重合率、技能空转浪费比率**。

### 8.3 战斗数据查询库（Data Explorer）

训练场页面除“运行模拟”外，还需要提供可查询、可核对的数据资料入口。这个能力归入 **Phase 3 / 阶段 F：Web 训练场 UI** 实现；数据本身仍由 **Phase 2 / 阶段 E：核心数据录入与校准** 负责补齐和校验。

- **职业与阵营查询**：按职业、阵营、输出/辅助定位技能，展示技能 ID、名称、阵营限制、重要度、默认使用频率等基础字段。
- **技能详情查询**：展示伤害附加、段数配置、CD、施法时间、充能、重置、命中时间、ActionType、是否 AOE 等字段。
- **Buff/Debuff 查询**：展示效果目标、持续时间、刷新规则、叠加层数、互斥组、覆盖策略、优先级、EffectPower 与具体 `BuffEffects` 数值。
- **Boss 数据查询**：展示副本、Boss 名称、等级、爆伤减免、伤害压缩、血量以及后续可能补充的攻击、防御等怪物属性。
- **来源与校验提示**：对暂缺、估算、待实测的数据做显式标记；允许从模拟配置中的技能、Buff、Boss 一键跳转到对应资料详情，避免玩家只能通过 JSON 查字段。

## 十、开发计划与验收标准

本章节用于指导实际开发执行。实施顺序应坚持“先引擎闭环，再扩大数据；先 CLI 可验证，再 Web 可视化；先逐段流水正确，再做聚合分析”的原则。

### 10.1 开发总原则

1. **公式单源**：伤害公式只能存在于共享引擎中，`agent_tool` 与 `web_app` 都调用同一套 `resolveHitDamage`。
2. **数据单源**：团队模拟所需技能、Buff、Debuff、功能技能都从 `skills.json` 读取；`combat_buffs.json` 仅服务旧版静态计算兼容。
3. **流水优先**：模拟器核心输出是 `HitDamageRecord[]` 与 `SimEvent[]`，总伤、DPS、占比、覆盖率都由流水聚合。
4. **小样例先行**：先用 1 个 Boss、1 个主输出、2-3 个辅助技能跑通闭环，再扩展到三输出与八辅助。
5. **可回归验证**：每个阶段都必须保留可重复运行的 CLI 或测试样例，防止 Web 展示掩盖引擎错误。

### 10.2 阶段 A：Workspace 与共享引擎基础

**目标**：建立可被 CLI 与 Web 同时引用的纯 TypeScript 模拟包。

**任务**
- 创建根目录 `package.json` 的 npm workspaces 配置。
- 新增 `packages/simulation-engine`，包含 `types`、数据加载适配、伤害公式、事件模型的导出入口。
- 将现有 `agent_tool/src/calculator.ts` 与 `web_app/src/utils/calculator.ts` 的重复公式合并到共享包。
- 保持旧 `agent_tool` 的单技能计算入口可运行，避免现有 skill 工作流中断。

**验收标准**
- `agent_tool` 仍可计算现有 profile，输出数值与迁移前一致。
- `web_app` 的静态计算结果与 `agent_tool` 使用同一共享函数。
- 项目根目录可以执行类型检查，且共享包没有浏览器/Node 专属副作用。
- 至少有一个回归样例证明迁移前后的单技能平均伤害一致。

### 10.3 阶段 B：数据 Schema 与 Profile 覆盖

**目标**：让 `skills.json` 能表达伤害技能、Buff、Debuff、功能技能和玩家个性化覆盖。

**任务**
- 扩展技能 schema：`ActionType`、`AppliesEffects`、`HitTiming`、`MaxCharges`、`ChargeReplenishTime`、`CooldownResets`、`MultiPhaseConfig`。
- 定义 profile 中的 `skillOverrides` 结构，支持覆盖 CD、施法时间、充能、命中时间、技能附加属性、状态持续时间和状态数值。
- 为 Boss 数据补充 `MonsterHealth`，并允许模拟输入临时覆盖 Boss 血量。
- 写数据校验工具，检查必填字段、非法目标、重复 `EffectId`、不存在的 `TargetSkillId`、互斥组配置缺失等问题。

**验收标准**
- 用白板技能和 profile 覆盖技能分别初始化 Actor，确认覆盖只影响本次模拟，不污染全局 `skills.json`。
- 同一个技能在不同玩家 profile 下能得到不同 CD、施法时间或 Buff 数值。
- JSON 示例能被解析，数据校验工具能发现缺字段、错 ID、非法枚举。
- Boss 没有血量时模拟器给出明确错误或要求 UI 手动输入，不静默使用 0 或无限血量。

### 10.4 阶段 C：离散事件模拟核心

**目标**：完成不依赖 UI 的战斗时间轴引擎。

**任务**
- 实现 `Timeline` 优先队列，支持按时间顺序处理 `CAST_START`、`CAST_COMPLETE`、`HIT`、`BUFF_APPLY`、`BUFF_EXPIRE`、`COOLDOWN_READY`、`PHASE_TRANSITION`、`ACTOR_DECISION`。
- 实现 Actor 运行时状态：施法锁定、GCD、技能 CD、充能层数、充能恢复事件。
- 实现三种主输出策略：手动时间轴、固定技能循环、法宝栏/天人合一。
- 实现辅助策略：起手铺垫期、CD 好了就放、绝对时间释放。
- 实现 `EffectManager`：持续时间、刷新、叠加、互斥组覆盖、实例级过期校验。
- 实现逐段命中：默认 `CastTime / HitCount` 均匀出段，特殊技能支持 `HitTiming.Offsets`。
- 实现 `resolveHitDamage`，每个 `HIT` 生成一条 `HitDamageRecord`。

**验收标准**
- 技能成功进入 `CAST_START` 时立即开始 CD，`CAST_COMPLETE` 不会重新启动 CD。
- 3 秒 9 段技能默认生成 9 条 `HitDamageRecord`，命中间隔符合 `CastTime / HitCount`。
- Buff 在第 N 段前过期时，第 N 段不再享受该 Buff；过期后聚合总伤能反映差异。
- 低效果互斥状态不能覆盖高效果状态；高效果状态能顶替低效果状态；旧过期事件不会误删新状态。
- Boss 血量归零时生成 `BOSS_DEAD`，后续未发生的命中不再计入伤害。
- 固定循环、法宝栏循环、手动时间轴在同一输入下输出稳定可复现。

### 10.5 阶段 D：CLI 与 Agent Skill 接入

**目标**：在 Web 开发前先获得可批量验证的模拟入口。

**任务**
- 新增 `agent_tool` 模拟 CLI，例如 `sim_cli.ts`，读取 `SimulationScenario` JSON 并输出结构化结果。
- 输出包含：resolved 配置、事件流水、逐段伤害流水、Boss 击杀时间、主输出 DPS 起点、技能占比、Buff/Debuff 覆盖率。
- 扩展现有分析脚本，使其可以基于整场模拟做技能顺序对比、队伍职业对比、属性边际对比。
- 保留旧单技能计算入口，避免影响现有边际分析流程。

**验收标准**
- CLI 可以在无浏览器环境下完成一次单 Boss 长时间模拟。
- CLI 输出 JSON 可被 Python runner 或 skill 脚本稳定解析。
- A/B 两个方案只改技能顺序时，报告能输出击杀时间差、总伤差、DPS 差和关键技能占比差。
- 属性扰动分析基于整场 `HitDamageRecord` 聚合，而不是静态单技能总伤。

### 10.6 阶段 E：核心数据录入与校准

**目标**：让首版覆盖三输出与八辅助，并保证数据可信。

**任务**
- 先录入最小闭环数据：1 个主输出、1 个 Boss、2-3 个关键辅助 Buff/Debuff。
- 再扩展到逐霜、太昊、涅羽核心输出技能。
- 录入天音、天华、昭冥、英招、画影、鬼王、焚香、青罗核心 Buff/Debuff 技能。
- 为每个技能补齐：目标、持续时间、CD、施法时间、是否可起手铺垫、互斥组、覆盖策略、效果数值。
- 对权威数据源和 JSON 录入结果做人工核对清单。

**验收标准**
- 每个首版职业至少有一组可运行样例，且不会因缺字段导致模拟中断。
- 关键 Buff/Debuff 的覆盖率能从事件流水中解释出来。
- 三个主输出职业的核心技能都能输出逐段伤害记录。
- 数据校验工具通过；所有跳过或暂缺的技能必须有明确备注，不参与默认模拟。

### 10.7 阶段 F：Web 训练场 UI

**目标**：让玩家可以配置队伍、技能循环、Boss，并直观看到模拟结果。

**任务**
- 新增团队模拟训练场页面或模式入口，不破坏现有静态计算页面。
- 实现队伍面板：6 人/12 人队伍、主输出选择、辅助职业选择、辅助技能开关。
- 实现主输出策略编辑：手动时间轴表格、固定循环列表、法宝栏 1-8 格拖拽。
- 实现 Boss 配置：副本/Boss 选择、Boss 血量展示、临时血量覆盖。
- 实现结果区：Boss 血量曲线、1 秒滚动伤害曲线、技能占比、Buff/Debuff 覆盖率、逐段伤害表。
- 实现方案 A/B 对比入口，允许锁定基准方案后修改配置并对比。
- 实现战斗数据查询库：支持按职业、阵营、技能类型、Buff/Debuff、Boss 检索，并能从模拟配置项跳转到对应详情。

**验收标准**
- 玩家能从空白页面完成一次“选择主输出、选 Boss、选辅助、配置循环、运行模拟”的闭环。
- 修改技能顺序或辅助职业后，结果能重新计算，并展示击杀时间和 DPS 差异。
- 逐段伤害表能定位到时间、技能、段数、伤害、参与结算的 Buff/Debuff。
- 玩家能在 UI 中查询任意已录入职业/阵营技能、Buff/Debuff 与 Boss 属性；暂缺或估算字段必须有明确标记。
- 页面刷新不会丢失当前主要配置，或至少支持导入/导出场景 JSON。
- 移动和桌面宽度下关键文本不重叠，时间轴和图表不会遮挡配置区。

### 10.8 阶段 G：分析、回归与发布

**目标**：把训练场从“能跑”提升为“可信、可比较、可复查”。

**任务**
- 增加回归测试：单技能伤害一致性、多段命中、Buff 过期、互斥覆盖、CD 起点、充能恢复、Boss 死亡截断。
- 增加模拟结果快照样例，固定输入必须输出稳定的击杀时间、总伤和技能占比。
- 增加异常输入处理：缺 Boss 血量、未知技能、互斥组冲突、手动指令到点不可用。
- 增加导出能力：场景 JSON、结果 JSON、关键表格复制。
- 更新 skill 文档，说明团队模拟 CLI 的输入格式、输出字段和报告口径。

**验收标准**
- 类型检查、核心测试和至少一个端到端模拟样例全部通过。
- 同一输入重复运行结果完全一致。
- 所有聚合数字都能追溯到 `HitDamageRecord`。
- 旧静态计算功能仍可使用。
- 用户可以拿到一份场景 JSON 和结果 JSON，复现同一次模拟。
