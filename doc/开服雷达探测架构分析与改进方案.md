# 开服雷达探测架构分析与改进方案

> 日期：2026-10-16 · 状态：待评审
> 范围：`functions/api/jiance.ts`、`web_app/src/components/tools/ServerRadarView.tsx`

## 一、当前状态（现状）

### 架构

```
浏览器(每个用户独立)
  ├─ 战区批量扫描：切换战区时一次拉全区（客户端缓存 30 分钟）
  └─ 单服持续监测：setInterval 每 4 秒 → GET /api/jiance?server=xxx
        ↓
Cloudflare Pages Function (functions/api/jiance.ts, 无状态边缘函数)
  ├─ 内存缓存 probeCache：Map，TTL 2000ms，仅 isolate 内有效
  ├─ 通道1：cloudflare:sockets 直连 {server}.link.zhuxian.com.cn:29000 (超时 1800ms)
  └─ 通道2（兜底）：HTTP 打 www.mujiston.com 第三方检测源 (超时 2200ms)
```

### 关键事实

- 探测完全由客户端轮询驱动；用户之间零去重（N 个用户 = N 份独立探测）。
- 内存缓存基本无效：TTL 2 秒 < 轮询间隔 4 秒，且 CF 边缘多 isolate 不共享，命中可忽略。
- 监测定时器在 `ServerRadarView` 组件的 `useEffect` 内，关闭右侧工作区（右上角 ×）即卸载组件、`clearInterval`，检测中断。
- **开服即停**：单服监测探测到 `status === 1` 后自动 `setIsProbing(false)` 停止轮询；若缓存已知在线，点击"启动监测"仅做一次校验不启动循环。实际轮询只发生在"维护中等开服"这一窗口期。
- 战区批量探测有 `.slice(0, 15)` 上限，单次最多并发 15 个服务器。
- 免费额度：Pages Functions 10 万次请求/天、KV 1,000 写/天、每请求 50 个子请求。

## 二、根因分析

问题不在代码质量，在于**职责放错了位置**：

1. **探测职责在客户端**。"某服现在什么状态"是全局事实，却由每个浏览器各自发起，探测次数随用户数线性增长，边缘层无法合并。
2. **缓存层级选错**。用 isolate 内存做缓存，而边缘计算天然多实例，缓存既短命（2s）又不共享，形同虚设。
3. **轮询节奏与状态变化速率不匹配**。服务器 99% 时间在线（状态不变），却恒定 4 秒一问；只有维护窗口（周二/周五 8:00 起，约 1~6 小时）状态才会变化。资源消耗与信息增益严重倒挂。

### 量化（按免费额度，最坏情况 = 全程维护中未开服）

| 场景 | 函数调用（最坏） | 上游探测 | 备注 |
|---|---|---|---|
| 1 人盯 1 服 1 小时 | 900 次 | 900 次（socket + 兜底 HTTP 最多 x2） | 若中途开服则即停，实际远低于此 |
| 10 人同时盯 1 服 1 小时（各自轮询） | 9,000 次 | 9,000 次，互不合并 | 同上 |
| 50 人盯 3 服 4 小时 | 约 21.6 万次 | 同量级，且全部砸向诛仙网关/小木匠 | 纯理论极端值 |

配额被雷达耗尽时，AI 问答等主业务接口一并 429 —— 非核心功能拖垮核心功能。

## 三、现阶段风险评级（用户量小、维护日约 1 小时）

诚实评估：**现阶段没有燃眉之急**。

- 平常日：无人挂机监测，只有零星"看一眼"请求（在线状态客户端缓存 30 分钟），日消耗百次级，完全无压力。
- 维护日：假设 5~10 人各盯 1~3 个服 1 小时，函数调用约 9,000~27,000 次/天，占免费额度 10%~27%。不爆，但一次"开服窗口 + 蹭热度"就可能翻几倍。
- 真正当前就存在的问题（与用户量无关）：
  1. **关页面检测就断**（组件内定时器随卸载销毁），用户体验缺陷；
  2. **对第三方（小木匠）的依赖是无节流的直打**，量小没事，但这是别人的免费资源，被蹭时无自保手段；
  3. 同一时刻所有盯同一服的用户各自探测，**状态翻转感知时刻可能差几秒**，且重复探测对官方网关是纯浪费。

结论：现状可用，改进属于**在用户量上来之前花小成本修架构**，不是救火。

## 四、推荐方案：订阅制事件驱动（DO + WebSocket + 自适应 alarm）

### 设计原则

1. **无人看 = 零探测**：无订阅者且状态在线时，DO alarm 停转，不消耗任何资源。
2. **有人看 = 全局只探一份**：每服一个 Durable Object，N 个订阅者共享同一探测循环（single-flight）。
3. **节奏自适应状态**：离线（维护中）→ alarm 10 秒；在线 → 300 秒。维护窗口自动变热轮询，开服瞬间全端秒级感知，无需写死任何"周二早八"规则。

### 架构

```
浏览器
  ├─ 打开监测：HTTP 查一次 DO 当前状态
  │    └─ 在线 → 降频轮询 300s（或停在"已开服"展示）
  │    └─ 离线 → 升级 WebSocket 订阅该服
  ├─ WS 断线：指数退避重连 + 重连时 HTTP 对齐一次状态
  └─ WS 不可达（代理/旧浏览器）：降级 HTTP 轮询 15s

RadarServerDO（每服一个，按服务器名分片）
  ├─ 有订阅者时：alarm 循环探测（离线 10s / 在线 300s 自续）
  ├─ offline→online 翻转瞬间：
  │    1. KV 写一次（radar:{server}，仅用于 DO 冷启动恢复）
  │    2. 向所有挂起 WebSocket 广播 → 所有订阅客户端同时响声
  └─ 订阅者清零且状态在线 → alarm 停止
```

关键技术选型：**WebSocket Hibernation**——连接由 runtime 托管，DO 休眠不计时长，只在 alarm/消息到达时苏醒，免费版可承载。

### 消耗量评估（免费额度）

| 项目 | 维护日 3 服 × 4h、50 人订阅 | 免费额度 | 结论 |
|---|---|---|---|
| DO 请求（alarm=探测） | ~4,300 次/天（最坏全天离线 ~2.6 万） | 10 万/天 | 安全 |
| Pages Function 调用（WS 建立+重连+兜底） | 数百次（原轮询方案同场景 ~7 万） | 10 万/天 | **降约 99%** |
| KV 写 | 状态翻转 ~10 次/天 | 1,000/天 | 安全（复用现有 GUESTBOOK namespace，radar: 前缀键） |
| 上游探测 | ~4,300 次，与人数无关 | — | 常量化 |

### 已识别的设计内行为与残留漏洞

- 页面关闭 = 订阅断开：维护中全员关页 → 探测暂停，下一人打开时冷启动恢复（可接受）。
- 关页后的声音提醒无解（浏览器限制）；如未来需要，走 Web Push，另行立项。
- WS 需降级路径（15s 轮询）兜底代理/旧环境。
- KV 只做冷启动恢复，绝不进实时热路径（最终一致性会毁掉秒级感知）。

| 文件 | 改动 | 规模 |

| `functions/durable/RadarServerDO.ts` | 新增：探测逻辑自 jiance.ts 平移 + alarm 自续 + WS hibernation 广播 + KV 翻转写 | ~200 行 |

## 六、实施顺序

1. DO + 薄路由（后端先行，前端不改也能跑通 HTTP 路径）

3. 真机验证：多浏览器同服订阅、断线重连、翻转广播、关页恢复
