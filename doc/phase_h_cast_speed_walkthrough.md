## 2. 施法缩短计算公式推导与差异分析

### 2.1 为什么之前的计算公式出错了？
在早期的仿真引擎实现中，使用的公式为：
`实际施法时间 = 基础施法时间 / ( (1 + 迅疾%) * (1 + 减少施法时间%) )`

在双 Buff 下（枕戈 50% 与龙战 36%）：
`实际施法时间 = 基础施法时间 / (1.50 * 1.36) = 基础施法时间 / 2.04`
* 苍龙啸理论时间：`3.0 / 2.04 = 1.47` 秒。
* 山雨理论时间：`2.0 / 2.04 = 0.98` 秒。

**弄错的根源**：  
旧版逻辑沿用了魔兽世界等 RPG 游戏常见的“急速速度分母增加”设计思路。然而，这种除法公式会导致在双 Buff 下的施法时间显著慢于游戏实测（苍龙啸实测为 1.0 秒，而旧公式算出来是 1.47 秒，误差高达 47%）。

### 2.2 底层真相：多乘区时间缩短乘算公式
通过对实测最快数据（苍龙啸 1.0 秒，山雨欲来 0.64 秒）的反推，证实了诛仙3底层的机制是**直接相乘进行时间减免**。

底层计算公式为：
`实际施法时间 = 基础施法时间 * (1 - 迅疾最大值%) * (1 - 减少施法时间%)`

* **枕戈待旦因子**：`(1 - 50%) = 0.50`
* **龙战于野因子**：`(1 - 36%) = 0.64`
* **合并减免系数**：`0.50 * 0.64 = 0.32`（即施法时间变为了原始的 32%，提速达到 3.125 倍）

**公式套用结果**：
* 苍龙啸理论时间：`3.0 * 0.32 = 0.96` 秒（与最快 1.00 秒极度贴合，包含 1 帧画面延迟）。
* 山雨欲来理论时间：`2.0 * 0.32 = 0.64` 秒（与最快 0.633 秒完全对齐，误差基本为 0）。

## 3. 迅疾 Buff 的优先级与多值互斥机制

需要澄清的是，同类的 Buff 在游戏底层无法重复叠加，而是采用**互斥且最高优先级覆盖**的规则：
* 例如：“枕戈待旦”（50% 迅疾）和“清啸横朔·曦日”（44% 迅疾）同属于“迅疾”类型的 Buff，属于同一个互斥组（在代码中属于 `ZS_HASTE_GROUP` 互斥组）。
* 游戏运行时会首先计算出当前所有活跃的迅疾 Buff 中的**最大值**（即 `swiftSpeedPercent = max(50, 44, ...)`）。
* 最终，这唯一的最大迅疾值代表了整个迅疾乘区，对应的时间因子为 `(1 - swiftSpeedPercent / 100)`。
* 而“龙战于野施法缩短 36%”属于另一独立的乘区，二者再次相乘。这完全保证了当未来出现 60%、80%、44% 等不同迅疾数值时，代码依然能够极其精准地模拟。
